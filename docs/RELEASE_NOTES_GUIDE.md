# 更新日志写作指南

本指南适用于 `CHANGELOG.md`、GitHub Release 和应用内更新说明。更新日志帮助用户判断要不要升级、升级后有什么变化；技术过程记录在 `docs/PROJECT_LOG.md` 或对应技术文档中。

## 写什么

优先写用户可以感知的变化：

- 新增了什么操作或能力。
- 哪个具体问题得到了修复，或哪种体验得到改善。
- 变化影响哪些场景或平台。
- 用户是否需要保存设置、重启应用或重新选择某项配置。

一条通常写一到两句。先写变化，再补充必要的使用条件或影响。没有实际用户影响的内部整理通常不必单列。

## 怎么写

1. **使用日常表达。** 写“切换模型后正确保存选择”，不要用函数、字段或协议实现代替用户问题。
2. **一个问题归为一条。** 同一修复涉及界面、保存和刷新时，合并说明最终效果，不按改了几个文件拆分。
3. **说清范围。** 只确认了某个平台或场景，就写明该范围。保留必要限制，不用“全面解决”“所有情况均正常”等无法证实的表述。
   安装限制应附上用户可执行的处理步骤，不要只堆放“未签名”“不能保证”等技术说明；涉及关闭某项系统防护时，写清具体开关及影响，不扩大为关闭其他防护。
4. **保留必要操作。** 会影响用户现有使用方式的变化，直接说明要做什么；不把关键条件藏在技术说明中。
5. **删除重复。** 检查相近条目是否描述同一收益，也检查标题、简介和正文是否重复表达同一句话。

下面仅比较写法，不表示这些变化已经在某个版本完成：

| 不推荐 | 推荐的写法 |
| --- | --- |
| 调整列表布局；调整卡片高度；调整滚动容器 | 供应商较多时，卡片仍能完整显示，列表可以独立滚动。 |
| 修复某内部字段校验和转换分支 | 修复部分供应商无法正常发送请求的问题。 |
| 更新权限异常捕获和错误映射 | 无法重启客户端时，显示具体原因和处理方法。 |

示例必须有实际改动和证据支撑后才能用于发布。若某个技术名称是用户排查问题所必需的，例如供应商名称、可见设置名称或特定文件名，可以保留；不附带内部变量、长堆栈或调试输出。

## 事实与验证

- 对照本次提交和实际交付内容写作，不把计划、尝试过的方案或排查猜测当作完成项。
- 区分“改善错误提示”和“解决错误根因”。只改善了提示，就按提示改善描述。
- 区分“可以保存设置”和“功能已经生效”。需要其他开关、可用账号或备用供应商时，写清条件。
- 编译、自动检查与实机观察各自能证明的范围不同，不用单一结果承诺全部平台、全部账号都可用。
- 未完成、未验证或暂时搁置的问题留在技术记录中，不为了让日志完整而宣称解决。

## 同一版本如何汇总

正式发布前，将该版本的本地迭代整理为一个条目：

1. 收集各次本地迭代最终保留的变化。
2. 按用户问题合并，删除重复、已撤回或已被后续方案替代的内容。
3. 只保留最终使用方式，不逐次叙述排查和修改过程。
4. 使用正式版本号与实际发布日期，移除该版本的本地测试标记。
5. 检查公开发布状态，避免把取消发布的候选版本当成已发布历史。

完整已发布历史继续保留在 `CHANGELOG.md`；单次 Release 或应用内说明只展示该版本的汇总，不重复整份历史日志。不要在没有需要的情况下重写已发布版本。

## 交付前复核

- 每条是否回答了“用户会看到什么变化”？
- 是否存在同一问题分成多条、或不同措辞的重复内容？
- 是否夹带实现细节、堆栈、未经证实的结论或未交付功能？
- 是否说明了必要的操作、适用范围和限制？
- 正式版本是否已汇总本地迭代，并使用正确的版本与日期？
- 排查过程和验证证据是否放在技术记录，而非用户更新说明中？

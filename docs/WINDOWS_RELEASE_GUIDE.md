# Windows 安装与在线更新约定

本文件记录 Windows 发布必须保留的能力及验证方式。维护者已明确要求：保留 MSI 安装包和安装版在线更新；未经明确同意，不得移除、改成仅手动下载，或用其他格式替换 MSI。

## 安装包与更新入口

- 默认安装包为 MSI，使用历史 UpgradeCode `1482a8e8-9217-517b-8528-93a6c90e0c2f`，使原 MSI 安装可以识别升级。
- `windows-x86_64` 和 `windows-x86_64-msi` 指向同一份签名 MSI；`windows-x86_64-nsis` 保留独立签名 EXE，服务已经安装 EXE 的用户。
- 旧 v0.3.21–v0.3.31 的 Windows 更新暂存器只接受 EXE。删除 NSIS 入口或把它直接指向 MSI，会破坏已安装客户端的更新，不能仅凭新客户端支持 MSI 就删除兼容包。
- 保留软件内检查、下载、Tauri 验签、官方 API 下载恢复、安装交接，以及失败时的路由恢复。便携版的手动更新约定不能扩展到安装版。
- 手动从 EXE 改装 MSI 前，应先退出并卸载 EXE 版，保留应用数据。MSI 检测已有 EXE 登记并阻止重复安装；不得执行未经验证的注册表卸载命令。
- 修正已发布版本应递增版本号。同版本重新打包不会被该版本客户端检测到；不得用修改更新格式代替正常版本升级。

## 发布前必须验证

1. 版本一致，MSI、兼容 EXE 及各自更新签名均存在；更新清单按安装类型选择正确文件，禁止将全部 Windows 项统一改指一种格式。
2. 在临时 Windows Actions 环境中验证 MSI 正常安装、重复安装、历史 MSI 升级、安装后窗口启动与存活、更新参数自动重新打开，以及配置文件摘要保持不变。
3. 保留原有 NSIS 安装及旧 MSI 迁移检查，不因恢复 MSI 而取消旧客户端兼容验证。
4. 安装检查失败时保留完整 MSI 日志，先确认失败阶段。已生成安装包不代表安装检查通过；安装检查的脚本异常也不应误判为编译失败。
5. 发布后核对公开清单、文件完整下载、大小及 SHA256。标准地址失败时可验证官方 API 回退，但须记录实际通道，不能称标准地址已通过。

安装检查只在临时 runner 上运行，不操作真实用户安装、会话或配置。不得终止 Windows Installer 服务；只可清理脚本明确追踪的测试应用。测试中模拟进程结束与验证产品真实退出回调是不同证据，报告必须区分。

## 已遇到的问题与固定处理

| 现象 | 原因及处理 |
| --- | --- |
| MSI 包中已有正确升级标识，脚本仍报标识不匹配 | PowerShell COM 属性读取未得到预期的纯属性值。用 Windows Installer 原生只读 API 查询，逐个检查返回码、关闭句柄，并保留严格标识比较。不要修改 UpgradeCode 来迎合错误读取结果。 |
| 已安装程序窗口能打开，测试等待退出超时 | Tauri 托盘应用的 `WM_CLOSE` 会隐藏窗口，`WM_QUIT` 也不是受支持的退出接口。不能把普通 Win32 消息当作 `app.exit`。包验证可明确模拟已跟踪测试进程结束，但不能据此宣称真实退出回调已测试。 |
| 检查草稿安装包时提示 release not found | GitHub 的草稿读取需要具有仓库写权限的工作流 token。独立 MSI 快验只下载测试，不修改草稿；不得为了读取而提前公开未经验证的包。 |
| 发布后的 Range 探测返回 504 | 使用完整下载并验证大小、摘要；标准下载和官方 API 回退分别记录结果。不能跳过内容校验。 |
| 智能应用控制拦截程序 | Windows 发布者信任与 Tauri 更新签名不同。更换 MSI 容器不能保证放行其中的 EXE/DLL；未配置发布者签名时须如实说明，不降低系统安全策略，不宣称已解决。 |

修复安装检查脚本时，可先用 `Windows MSI package verification` 对现有草稿包快验，避免每次排查都重编所有平台；最终发布仍须完成正式 Release 流程。
